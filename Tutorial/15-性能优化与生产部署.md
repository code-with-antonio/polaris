## 二、Next.js 构建优化

### 2.1 next.config.ts 完整解析

```tsx
// next.config.ts
import { withSentryConfig } from "@sentry/nextjs";
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  // 配置必要的安全 headers
  async headers() {
    return [
      {
        source: "/:path*",
        headers: [
          // WebContainer 必须的安全 headers
          { key: "Cross-Origin-Embedder-Policy", value: "credentialless" },
          { key: "Cross-Origin-Opener-Policy", value: "same-origin" },
        ],
      }
    ];
  }
};

export default withSentryConfig(nextConfig, {
  org: "john-doe-fb",
  project: "polaris",

  // 只在 CI 环境打印上传日志，本地构建保持安静
  silent: !process.env.CI,

  // 上传更大的 source map 集合，获得更精确的错误堆栈
  widenClientFileUpload: true,

  // 通过 Next.js 重写路由来绕过广告拦截器
  tunnelRoute: "/monitoring",

  webpack: {
    // 自动 Vercel Cron 监控
    automaticVercelMonitors: true,

    // Tree-shaking：移除 Sentry 调试日志，减小打包体积
    treeshake: {
      removeDebugLogging: true,
    },
  }
});
```

**关键优化点解读：**

#### `tunnelRoute: "/monitoring"`

默认情况下，Sentry 的浏览器 SDK 直接向 Sentry 的域名发送请求，容易被广告拦截器拦截。`tunnelRoute` 让请求先经过 Next.js 自己的服务器，再转发到 Sentry：

```
浏览器 → /monitoring (Next.js 路由) → Sentry 服务器
```

好处：
- 绕过广告拦截器
- 避免跨域问题
- 减少被 CORS 策略阻止的可能

#### `widenClientFileUpload: true`

上传更完整的 source map，让 Sentry 能展示更精确的错误堆栈，定位到具体的源码行。

#### `treeshake.removeDebugLogging: true`

生产构建时自动移除 Sentry 内部的调试日志调用，减小最终 bundle 体积。

### 2.2 COOP/COEP Headers 的重要性

```tsx
{ key: "Cross-Origin-Embedder-Policy", value: "credentialless" },
{ key: "Cross-Origin-Opener-Policy", value: "same-origin" },
```

这两个 headers **不是可选的**。WebContainer API 需要 `SharedArrayBuffer`，而 `SharedArrayBuffer` 要求：
- `Cross-Origin-Opener-Policy: same-origin` — 防止跨源窗口共享
- `Cross-Origin-Embedder-Policy: credentialless` — 允许无凭证跨源嵌入

没有这两个 headers，WebContainer 无法启动，浏览器终端功能将完全失效。

## 三、Convex 查询优化

### 3.1 索引设计

Convex 数据库的性能取决于索引是否合理。Polaris 为每张表精心设计了索引：

```tsx
// convex/schema.ts
projects: defineTable({...})
  .index("by_owner", ["ownerId"])
  // 用户首页只查询自己拥有的项目

files: defineTable({...})
  .index("by_project", ["projectId"])
  .index("by_parent", ["parentId"])
  .index("by_project_parent", ["projectId", "parentId"])
  // 复合索引：按项目 + 父 ID 查询，最常见的文件查询模式

conversations: defineTable({...})
  .index("by_project", ["projectId"])

messages: defineTable({...})
  .index("by_conversation", ["conversationId"])
  .index("by_project_status", ["projectId", "status"])
  // 复合索引：按项目 + 状态查询，用于查找处理中的消息
```

**索引与查询的对应关系：**

| 查询场景 | 使用的索引 | 查询方法 |
|---------|-----------|---------|
| 获取用户所有项目 | `by_owner` | `.withIndex("by_owner", q => q.eq("ownerId", ...))` |
| 获取项目所有文件 | `by_project` | `.withIndex("by_project", q => q.eq("projectId", ...))` |
| 获取文件夹内容 | `by_project_parent` | `.withIndex("by_project_parent", q => q.eq("projectId", ...).eq("parentId", ...))` |
| 获取对话列表 | `by_project` | `.withIndex("by_project", q => q.eq("projectId", ...))` |
| 获取对话消息 | `by_conversation` | `.withIndex("by_conversation", q => q.eq("conversationId", ...))` |
| 获取处理中的消息 | `by_project_status` | `.withIndex("by_project_status", q => q.eq("projectId", ...).eq("status", "processing"))` |

> **关键原则：每个查询都使用 `.withIndex()`，绝不进行全表扫描。**

### 3.2 分页与限制

Polaris 提供了两种获取项目列表的方式：

```tsx
// 方式一：获取全部项目（用于项目数量较少的场景）
export const get = query({
  args: {},
  handler: async (ctx) => {
    return await ctx.db
      .query("projects")
      .withIndex("by_owner", (q) => q.eq("ownerId", identity.subject))
      .order("desc")
      .collect();
  },
});

// 方式二：获取前 N 个项目（用于首页懒加载）
export const getPartial = query({
  args: { limit: v.number() },
  handler: async (ctx, args) => {
    return await ctx.db
      .query("projects")
      .withIndex("by_owner", (q) => q.eq("ownerId", identity.subject))
      .order("desc")
      .take(args.limit);  // ← 只取前 N 条
  },
});
```

**前端使用：**

```tsx
// 首页 - 分页加载项目
export const useProjectsPartial = (limit: number) => {
  return useQuery(api.projects.getPartial, { limit });
};
```

**优化建议：**
- 当用户项目超过 50 个时，使用 `getPartial` 替代 `get`
- 滚动加载更多时逐步增加 limit 值
- 避免一次性加载大量数据

### 3.3 条件查询：`"skip"` 模式

```tsx
// 当 projectId 为 null 时跳过查询，避免无效请求
export const useFiles = (projectId: Id<"projects"> | null) => {
  return useQuery(api.files.getFiles, projectId ? { projectId } : "skip");
};
```

**工作原理：** 当第二个参数为字符串 `"skip"` 时，Convex 不会发送任何查询请求，直接返回 `undefined`。这在组件挂载时参数尚未就绪的场景下非常有用。

## 四、乐观更新优化

### 4.1 Convex 乐观更新模式

Polaris 在文件操作（创建、重命名、删除）中大量使用乐观更新，让用户感觉操作是即时的：

```tsx
export const useCreateFile = () => {
  return useMutation(api.files.createFile).withOptimisticUpdate(
    (localStore, args) => {
      // 1. 获取当前本地查询结果
      const existingFiles = localStore.getQuery(api.files.getFolderContents, {
        projectId: args.projectId,
        parentId: args.parentId,
      });

      if (existingFiles !== undefined) {
        const now = Date.now();
        const newFile = {
          _id: crypto.randomUUID() as Id<"files">,
          _creationTime: now,
          projectId: args.projectId,
          parentId: args.parentId,
          name: args.name,
          content: args.content,
          type: "file" as const,
          updatedAt: now,
        };

        // 2. 立即更新本地查询结果
        localStore.setQuery(
          api.files.getFolderContents,
          { projectId: args.projectId, parentId: args.parentId },
          sortFiles([...existingFiles, newFile])
        );
      }
    }
  );
};
```

**执行流程：**

```
用户点击"新建文件"
    ↓
乐观更新：立即在 UI 中插入新文件（无延迟感）
    ↓
后台发送 Mutation 请求到 Convex
    ↓
Convex 处理完成
    ↓
useQuery 自动收到真实结果，替换乐观数据
    ↓
如果 Mutation 失败 → 乐观数据回滚
```

### 4.2 重命名更新的级联更新

```tsx
export const useRenameFile = ({ projectId, parentId }) => {
  return useMutation(api.files.renameFile).withOptimisticUpdate(
    (localStore, args) => {
      // 同时更新两个查询：文件夹内容 + 文件详情
      localStore.setQuery(
        api.files.getFolderContents, { projectId, parentId },
        sortFiles(updatedFiles)
      );
    }
  );
};
```

### 4.3 删除的乐观更新

```tsx
export const useDeleteFile = ({ projectId, parentId }) => {
  return useMutation(api.files.deleteFile).withOptimisticUpdate(
    (localStore, args) => {
      const existingFiles = localStore.getQuery(api.files.getFolderContents, {
        projectId, parentId,
      });
      if (existingFiles !== undefined) {
        // 从本地查询结果中过滤掉被删除的文件
        localStore.setQuery(
          api.files.getFolderContents,
          { projectId, parentId },
          existingFiles.filter((file) => file._id !== args.id)
        );
      }
    }
  );
};
```

## 五、Sentry 错误追踪集成

### 5.1 四层 Sentry 配置

Polaris 在四个运行时环境中分别配置了 Sentry：

```
src/
  instrumentation.ts           ← 服务端注册（Node.js + Edge）
  instrumentation-client.ts    ← 浏览器端配置
  app/global-error.tsx         ← 全局错误边界
sentry.server.config.ts        ← Node.js 运行时配置
sentry.edge.config.ts          ← Edge 运行时配置
```

### 5.2 服务端注册入口

```tsx
// src/instrumentation.ts
import * as Sentry from "@sentry/nextjs";

export async function register() {
  if (process.env.NEXT_RUNTIME === "nodejs") {
    await import("../sentry.server.config");
  }
  if (process.env.NEXT_RUNTIME === "edge") {
    await import("../sentry.edge.config");
  }
}

// 自动捕获 API 路由请求错误
export const onRequestError = Sentry.captureRequestError;
```

**`register()` 函数**是 Next.js 的特殊导出，在服务器启动时执行一次。通过 `NEXT_RUNTIME` 环境变量区分运行环境。

**`onRequestError`** 自动捕获所有 API 路由的错误，无需手动调用 `Sentry.captureException()`。

### 5.3 客户端配置

```tsx
// src/instrumentation-client.ts
import * as Sentry from "@sentry/nextjs";

Sentry.init({
  dsn: "https://...@...ingest.de.sentry.io/...",

  integrations: [Sentry.replayIntegration()],

  // 性能追踪采样率（生产环境应降低此值）
  tracesSampleRate: 1,

  // 启用日志发送到 Sentry
  enableLogs: true,

  // Replay：正常会话采样 10%
  replaysSessionSampleRate: 0.1,

  // Replay：错误发生时 100% 采样
  replaysOnErrorSampleRate: 1.0,

  // 允许发送用户个人信息（用于调试）
  sendDefaultPii: true,
});

// 捕获 Next.js App Router 路由转换事件
export const onRouterTransitionStart = Sentry.captureRouterTransitionStart;
```

**Replay 功能详解：**
- `replaysSessionSampleRate: 0.1` — 10% 的普通用户会话会被录制（节省 Sentry 配额）
- `replaysOnErrorSampleRate: 1.0` — 当用户遇到错误时，100% 录制该会话的 Replay
- **Replay 不是视频**，而是用户操作的重放（DOM 变更 + 交互事件），体积远小于视频

### 5.4 Server/Edge 运行时配置

```tsx
// sentry.server.config.ts
Sentry.init({
  dsn: "...",
  tracesSampleRate: 1,
  enableLogs: true,
  sendDefaultPii: true,
  integrations: [
    // AI 功能集成：追踪 LLM 调用
    Sentry.vercelAIIntegration,
    // 将 console.log/warn/error 作为日志发送到 Sentry
    Sentry.consoleLoggingIntegration({ levels: ["log", "warn", "error"] }),
  ],
});
```

**关键 Integration：**

| Integration | 作用 |
|-------------|------|
| `vercelAIIntegration` | 自动追踪 AI SDK 的 LLM 调用（模型、token 用量、响应时间） |
| `consoleLoggingIntegration` | 将 `console.error/warn/log` 转发到 Sentry 日志 |

### 5.5 全局错误边界

```tsx
// src/app/global-error.tsx
"use client";

import * as Sentry from "@sentry/nextjs";
import NextError from "next/error";
import { useEffect } from "react";

export default function GlobalError({
  error,
}: {
  error: Error & { digest?: string };
}) {
  useEffect(() => {
    Sentry.captureException(error);
  }, [error]);

  return (
    <html lang="en">
      <body>
        <NextError statusCode={0} />
      </body>
    </html>
  );
}
```

**为什么需要 GlobalError：**
- `global-error.tsx` 是 Next.js App Router 的最顶层错误边界
- 它捕获**所有**未被其他错误边界处理的错误（包括布局错误）
- `useEffect` 中将错误发送到 Sentry
- 渲染默认的 Next.js 错误页面

**错误边界层级：**

```
GlobalError (最顶层)
  ├── Layout Error
  └── Page Error
        ├── Error Boundary 组件 (业务自定义错误处理)
        └── Component Error
```

### 5.6 Inngest + Sentry 中间件

```tsx
// src/inngest/client.ts
import { inngest } from "./client";
import { sentryInngestMiddleware } from "@inngest/middleware-sentry";

// Sentry 中间件自动为每个 Inngest 函数调用创建 Span
inngest.addMiddleware(sentryInngestMiddleware);
```

这样 Inngest 后台任务的执行也会被 Sentry 追踪，可以看到每个后台函数的耗时和错误。

## 九、常见问题与排查

### 9.1 WebContainer 无法启动

**症状：** 终端页面空白，WebContainer 连接失败

**排查：**
1. 检查 Response Headers 是否包含 COOP/COEP
2. 浏览器 DevTools Console 查看是否有 `SharedArrayBuffer is not defined` 错误
3. 确认 `next.config.ts` 中的 headers 配置正确

### 9.2 Sentry 不收到错误

**排查：**
1. 检查 `SENTRY_DSN` 环境变量是否正确设置
2. 检查广告拦截器是否拦截了 Sentry 请求
3. 确认 `tunnelRoute` 配置的路由未与 Next.js Middleware 冲突
4. 检查 Source Map 是否成功上传：Sentry Dashboard → Settings → Source Maps

### 9.3 Convex 查询慢

**排查：**
1. 检查查询是否使用了 `.withIndex()`
2. 检查索引字段是否与查询条件匹配
3. 数据量大时考虑使用 `take(N)` 分页

### 9.4 Inngest 函数不执行

**排查：**
1. 确认 Inngest Dev Server 正在运行
2. 检查 `INNGEST_EVENT_KEY` 环境变量
3. 在 Inngest Dashboard 查看事件日志
4. 确认函数已在 `/api/inngest` 路由中注册
